# Testing Practices Baseline

Status: active
Version: 0.1.0

General testing-practice discipline that applies regardless of language,
framework, or test runner: keeping individual tests self-contained, choosing
the right coverage layer before adding a new test, treating a remote test
environment's build as a variable the agent must check rather than assume,
and localizing batch failures to the test harness before blaming the
product. This baseline is deliberately not language- or framework-specific;
see the relevant conventions baseline for that repo's stack instead.

## Principles

1. A test whose expected result depends on an external mutable config it
   cannot itself set is not self-contained.
   If two test cases need opposite settings on the same shared target (a
   feature flag, an environment variable, a config row in a shared database,
   a remote service's runtime setting), they can never both pass in the same
   run — whichever ran second inherits whatever state the first one left
   behind, or whatever state some other process left behind. Either own the
   setting end to end (set it at the start of the test, restore the prior
   value when the test ends, including on failure) or run against a fixture
   or isolated instance where the value is already baked in and nothing else
   can change it mid-run. A test that merely assumes a setting's current
   value, without setting or verifying it, is not testing that behavior — it
   is testing whatever the last writer left behind.

2. Before adding a test, ask what behavior it actually verifies and where
   that behavior's existing coverage already lives.
   A new test is not free: it adds runtime, flakiness surface, and future
   maintenance burden, and a high-maintenance end-to-end test that
   re-verifies behavior already stably covered by a unit test one layer down
   adds cost without adding confidence. Check whether the behavior in
   question is already exercised at a cheaper, faster, more isolated layer
   before reaching for the more expensive one. Add the expensive test only
   for what the cheaper layer genuinely cannot observe — an integration
   boundary, a cross-service contract, a real end-to-end path a unit test
   cannot simulate.

3. Approval and end-to-end tests that run against a shared remote
   environment reflect whatever build is currently deployed there, not your
   local code.
   Before accepting a batch of failing snapshots or approvals as real
   behavior changes worth approving, confirm the deployed build actually
   includes the changes under test. Never approve new baselines generated by
   an environment that isn't yet running the new code — doing so bakes the
   old (or half-deployed) behavior in as the new expected result, and the
   next run against the correct build will fail against a baseline that was
   never actually correct. When a remote-environment test run produces
   unexpected results, checking what build is live is a cheaper first step
   than re-deriving the expected behavior from scratch.

4. When requests all technically succeed but a whole batch of test
   assertions fails uniformly, suspect a shared test-harness assumption
   before assuming the product has many independent bugs.
   A response-parsing path, a shared setup fixture, an assertion helper, or
   an auth/session step used by every test in the batch is a much more
   likely single point of failure than the product independently breaking in
   the same way across many unrelated cases at once. Use one passing peer
   test that exercises a known-correct read path as contrast: if it passes
   while the rest fail on the same kind of assertion, the fault is
   localized to whatever differs between that peer and the failing batch —
   usually the harness — not to the product under test.

## Priority

Apply this baseline before ordinary test-writing and test-triage habits, but
never use it to override explicit user instructions, safety rules, privacy
boundaries, or stricter repo-local instructions.

## Non-Goals

- This does not mandate a specific test framework, runner, or coverage
  percentage — it describes correctness and diagnostic properties the
  agent's testing judgment should have, however the repo chooses to
  implement tests.
- This does not cover CI pipeline configuration (triggers, parallelization,
  caching, gating) — see repo-local CI docs for that.
- This is not a language- or framework-specific testing guide; pair it with
  the repo's own conventions baseline (e.g. `dotnet-conventions`,
  `python-conventions`) for stack-specific testing details.
